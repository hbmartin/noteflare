## Prepare and verify resources

`pnpm platform:provision plan production` reads current resources without changing the account. `pnpm platform:provision apply production` creates missing private publication/audit buckets, installs retention policies, creates the 384-dimensional cosine Vectorize index and its string spaceId metadata index, and creates the canonical-host Turnstile widget. It does not buy subscriptions. Staging uses the same commands with `staging`, separate resources and the notes-staging/public-staging hostnames.

Policies preserve unrelated rules. Audit objects and manifests under `audit/` are locked for 365 days. Managed cleanup waits at least that long after both uploads, including when the configured archive period is shorter. A failed cleanup retains the archive pointer while processing other eligible archives. On the next maintenance run, a recognized transient failure is eligible for retry after ten minutes. A lock, an incomplete delete, or an unclassified failure is eligible after one day. Owner access expires at the stored `expires_at` regardless of cleanup timing. Raising the archive period can extend physical storage for existing archives while their owner-access expiry remains fixed. The owner platform API reports the configured period, the applicable dedicated-bucket lock floor, and the configured storage minimum. Link preview images expire after two days. A failed metadata refresh keeps the title and description and retires the previous image reference. Disposable `job-artifacts/` copies expire after eight days, with application cleanup reclaiming completed attempts after the seven-day download window. Active and retryable `jobs/` sources remain eligible for resumption. R2 may apply lifecycle deletions later than their eligibility time.

The new widget secret is written to an ignored, private Turnstile environment file beneath `.wrangler/platform/`. Do not commit it or paste it into logs. To create unreachable Worker shells and install identity secrets, supply the existing production installation's `BETTER_AUTH_SECRET` through the environment and run `pnpm platform:provision bootstrap production`. This preserves installed identity secrets. Staging generates or reuses its own identity and setup key in a private, ignored bootstrap environment file. To restore staging credentials from a secure record, use `PLATFORM_STAGING_BETTER_AUTH_SECRET` and `PLATFORM_STAGING_BOOTSTRAP_TOKEN`. Bootstrap keeps new Worker ingress disabled until final deployment. It initializes identity and Analytics credentials independently of Turnstile. It can fill a missing Turnstile secret on a Worker whose live sitekey matches the managed widget.

A Worker with Turnstile disabled and neither a sitekey nor secret receives its first pair in the ordinary coordinated release. Live preflight verifies that the Worker is still eligible and that the managed widget covers both canonical hostnames. If one upload succeeds, prepare again so the retry pairs only the remaining clean Worker. An existing Turnstile secret without a live sitekey has unknown pairing and requires `--replace-turnstile` or the matching workflow option.

For widget replacement, rename the previous widget and keep it active for rollback. Provision the new widget under the environment's managed name with both canonical hostnames. Then prepare with `--replace-turnstile` or select `replace_turnstile_widget` in a fresh production workflow dispatch. Use the same explicit release for secret rotation on an unchanged widget and complete the release within Cloudflare's grace period. The coordinated deployment checks the prepared sitekey and fetches its secret from Cloudflare. It uploads the pair in the same version of each Worker, using a temporary private file for the secret. Previously opened challenge pages may need a reload. If a partial upload stops the release, read back both live settings and prepare again with explicit replacement. Keep the previous widget available while the new pair is being verified. [Turnstile secret rotation](https://developers.cloudflare.com/turnstile/troubleshooting/rotate-secret-key/)

No administrative API token belongs on public delivery. Its only secrets are BETTER_AUTH_SECRET and TURNSTILE_SECRET_KEY.

Install it as CF_ANALYTICS_API_TOKEN on each application Worker that will report costs. Create a separate token restricted to the sparkedinnovations.training zone with Zone WAF Edit for the edge rules; keep it in the deployment environment only. ## Migration rehearsal and cutover

Run `node scripts/rehearse-platform-migrations.mjs` to export only production schema and migration metadata, reconstruct the current migration point in an isolated local D1 store, and apply pending migrations there. Its evidence file records the source and target migrations. It never applies a migration to production or copies application records. Data-dependent repairs are additionally covered by integration fixtures.

Production was observed at 0069 during planning, so the existing Slack upgrade procedure applies: pause delivery and channel validation and drain invocations for 16 minutes before migration. Preserve every existing quiescence confirmation and publication compatibility requirement in [UPGRADING](../UPGRADING.md) and the [platform release](cloudflare-platform-release.md).

Migration `0115_audit_cleanup_deadline.sql` adds a nullable cleanup deadline without rewriting existing archive expiry timestamps. Apply it before uploading the Worker that uses the new column. A pre-upgrade cleanup deferral may already have extended an archive's stored expiry. In that case the archive can remain listed until that expiry, and downloads return `503` if its data object was already deleted. The original expiry cannot be inferred reliably from the database row.

Apply migration `0116_platform_job_redispatch.sql` before uploading the Worker that uses Queue redispatch state. Existing jobs retain their execution and lease deadlines. After Queue accepts a normal or recovery send and its deadline is recorded, recovery waits five minutes from when the message becomes eligible for delivery. A failed recovery send backs off per job from one minute to one hour. When phase 2 cannot record a deadline, the coordinator uses the later of the intended deadline and a cooldown that grows from one minute to one hour after repeated write failures. The recovery phase also backs off when all Queue sends in a batch fail or all deadline writes fail. Publication maintenance sends in phase 1 and records deadlines in groups of up to ten. If a group's write fails, the coordinator uses the same cooldown to preserve the grace period for those accepted sends. Request and consumer wakes report a failed deadline write to the coordinator for the same cooldown. A wake that cannot read the job's dispatch state records no deadline, so recovery may send that job again.

The coordinator keeps up to 100 cooldowns. Within a job incarnation identified by its ID and creation timestamp, newer dispatch revisions supersede older ones. A successful deadline write clears cooldowns through the revision it wrote. On overflow the coordinator drops entries D1 confirms belong to a changed or finished job, then expired entries. If the current incarnation is unknown, it favors an active stored cooldown over an incoming report for a different incarnation of that job. If it still needs room, it evicts previously stored active cooldowns with the earliest deadlines. Phase 2 checks the current cooldowns before each Queue send. If a recheck fails, it stops that batch, saves the preceding dispatch outcomes, and applies the phase backoff.

If cooldown storage returns a catchable error during maintenance, the phase records its usual backoff. A disk-flush failure can reset the Durable Object, in which case Cloudflare handles alarm retries. Rerunning phase 1 sweeps for missing publication intents, so jobs with existing intents may be redispatched before their grace periods if their cooldowns were lost. The owner’s Retry button resets eligible jobs in that workspace and wakes the coordinator. The recovery phase keeps its outage backoff.

Before changing origins, verify owner password plus MFA/recovery access. Update OAuth/Slack callbacks and client integration endpoints. Set the GitHub production environment's PRODUCTION_BASE_URL to the application origin. Confirm staging acceptance and set PLATFORM_CUTOVER_READY=true only for the verified initial cutover. Subsequent deployments recognize the already-canonical live origin. Enroll and test a new-origin passkey after cutover.

## Edge controls and API schemas

Run `pnpm platform:provision edges-plan production` with the scoped edge token, review the result, then use edges-apply. Existing unrelated rules remain intact. The Free plan's one rate rule combines Forms and share paths at 100 requests per source IP per ten seconds with a ten-second block. Because Free expressions are path-only, matching paths on the application hostname are included. Hostname-scoped custom rules restrict public interaction methods. The command discovers the advertised Free managed ruleset and explicitly deploys it for the four reviewed application/public hostnames across production and staging, then verifies its execution rule by readback. Existing operator-managed execution rules and overrides are preserved and reported for scope review. No paid ruleset is selected. See [managed ruleset availability](https://developers.cloudflare.com/waf/managed-rules/) and [zone deployment via API](https://developers.cloudflare.com/waf/managed-rules/deploy-api/).

Production and staging have separate hostname-method and schema-mitigation rule references. They share the one zone-wide, path-only rate rule. Rule writes and activated schema evaluation are read back before configuration reports success. An occupied allowance stops preflight without replacing another application's rules.

Live readback initially found no managed-phase entry point despite the available Free ruleset. Explicit Free execution is now installed for the approved hostnames and verified. Its deployment does not consume either of the custom-rule slots or the single rate-rule slot.

Worker validation always uses the shared Zod catalog for the 23 current /v1 routes. `pnpm api:schema` regenerates bundled full and edge OpenAPI documents in docs/api; `pnpm api:schema:check` detects drift. Existing authorization, semantic content validation, Notion error envelopes and the bounded 500 KiB body reader remain in place.

API Shield entitlement is separate from a zone's uploaded-schema limits. Without entitlement the release reports Worker enforcement and leaves edge schema protection unavailable. With existing entitlement, set CF_SCHEMA_ENTITLED=true to upload/register and activate edge evaluation. Only after representative-traffic analysis set CF_SCHEMA_EVALUATED=true to add the hostname-scoped block rule. The edge document omits bodies because valid writes can exceed Free's 1 KiB inspection limit; the Worker retains body enforcement. No subscription is automatically enabled.
